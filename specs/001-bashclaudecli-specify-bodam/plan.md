# 구현 계획: 커피 기부 플랫폼 보담(BoDam) - 소방대원 지원 서비스

**브랜치**: `001-bashclaudecli-specify-bodam` | **날짜**: 2025-09-19 | **명세서**: [spec.md](./spec.md)
**입력**: `/specs/001-bashclaudecli-specify-bodam/spec.md`의 기능 명세서

## 실행 흐름 (/plan 명령어 범위)
```
1. 입력 경로에서 기능 명세서 로드
   → 찾을 수 없으면: ERROR "경로 {path}에 기능 명세서 없음"
2. 기술적 맥락 작성 (NEEDS CLARIFICATION 스캔)
   → 프로젝트 유형 감지 (web=프론트엔드+백엔드, mobile=앱+API)
   → 프로젝트 유형에 따른 구조 결정
3. 헌법 문서 내용 기반으로 헌법 검사 섹션 작성
4. 아래 헌법 검사 섹션 평가
   → 위반사항 존재시: 복잡도 추적에 문서화
   → 정당화 불가능시: ERROR "먼저 접근방식 단순화"
   → 진행 추적 업데이트: 초기 헌법 검사
5. 0단계 실행 → research.md
   → NEEDS CLARIFICATION 남아있으면: ERROR "미해결 사항 해결"
6. 1단계 실행 → contracts, data-model.md, quickstart.md, 에이전트별 템플릿 파일
7. 헌법 검사 섹션 재평가
   → 새로운 위반사항시: 설계 리팩터링, 1단계로 복귀
   → 진행 추적 업데이트: 설계 후 헌법 검사
8. 2단계 계획 → 작업 생성 접근방식 설명 (tasks.md 생성하지 않음)
9. 중지 - /tasks 명령어 준비 완료
```

**중요**: /plan 명령어는 7단계에서 중지됩니다. 2-4단계는 다른 명령어로 실행:
- 2단계: /tasks 명령어가 tasks.md 생성
- 3-4단계: 구현 실행 (수동 또는 도구 사용)

## 요약
소방서별 커피 기부를 통한 소방대원 지원 플랫폼으로, 실시간 화재 사건 추적, AI 기반 콘텐츠 분석, 결제 처리, 기부 관리 기능을 포함합니다. Next.js 프론트엔드, 비동기 기능을 갖춘 FastAPI 백엔드, AI 기능용 벡터 확장이 있는 PostgreSQL, 모니터링 및 CI/CD 자동화를 포함한 Kubernetes 기반 인프라로 구성됩니다.

## 기술적 맥락
**언어/버전**: Python 3.11+ (백엔드), TypeScript/Node.js 18+ (프론트엔드)
**주요 의존성**: FastAPI, SQLAlchemy, Next.js, TailwindCSS, Celery, Redis
**저장소**: PostgreSQL + pgvector + PostGIS, Redis (캐시/큐), Nginx 정적 파일
**테스트**: pytest + httpx (백엔드), Jest + Playwright (프론트엔드), Tavern (E2E), k6 (성능)
**대상 플랫폼**: Kubernetes (Linux 컨테이너), Vercel (프론트엔드 배포)
**프로젝트 유형**: 웹 - 마이크로서비스 아키텍처를 가진 프론트엔드 + 백엔드
**성능 목표**: p95 < 300ms 응답시간, 1000+ 동시 사용자, 30분 데이터 새로고침 주기
**제약사항**: ≥70% 테스트 커버리지, <1% 실패율, 99.9% 가용성, 실시간 WebSocket 알림
**규모/범위**: 10k+ 사용자, 소방서 데이터 통합, AI 콘텐츠 분석, 결제 처리

## 0단계: 개요 및 연구
1. **위의 기술적 맥락에서 미해결 사항 추출**:
   - 각 NEEDS CLARIFICATION → 연구 작업
   - 각 의존성 → 모범사례 작업
   - 각 통합 → 패턴 작업

2. **연구 에이전트 생성 및 파견**:
   ```
   기술적 맥락의 각 미해결 사항에 대해:
     작업: "{기능 맥락}을 위한 {미해결 사항} 연구"
   각 기술 선택에 대해:
     작업: "{도메인}에서 {기술}의 모범사례 찾기"
   ```

3. **연구 결과 통합** `research.md`에서 다음 형식 사용:
   - 결정: [선택된 것]
   - 근거: [선택된 이유]
   - 고려된 대안: [평가된 다른 것들]

**출력**: 모든 NEEDS CLARIFICATION이 해결된 research.md

## 1단계: 설계 및 계약서
*선행조건: research.md 완료*

1. **기능 명세서에서 엔티티 추출** → `data-model.md`:
   - 엔티티명, 필드, 관계
   - 요구사항의 검증 규칙
   - 해당시 상태 전이

2. **기능 요구사항에서 API 계약서 생성**:
   - 각 사용자 액션 → 엔드포인트
   - 표준 REST/GraphQL 패턴 사용
   - OpenAPI/GraphQL 스키마를 `/contracts/`에 출력

3. **계약서에서 계약 테스트 생성**:
   - 엔드포인트당 하나의 테스트 파일
   - 요청/응답 스키마 검증
   - 테스트는 실패해야 함 (아직 구현 없음)

4. **사용자 스토리에서 테스트 시나리오 추출**:
   - 각 스토리 → 통합 테스트 시나리오
   - 빠른시작 테스트 = 스토리 검증 단계

5. **에이전트 파일 점진적 업데이트** (O(1) 연산):
   - AI 어시스턴트용 `.specify/scripts/bash/update-agent-context.sh claude` 실행
   - 존재시: 현재 계획의 새로운 기술만 추가
   - 마커 사이 수동 추가 사항 보존
   - 최근 변경사항 업데이트 (최근 3개 유지)
   - 토큰 효율성을 위해 150줄 이하 유지
   - 저장소 루트에 출력

**출력**: data-model.md, /contracts/*, 실패하는 테스트, quickstart.md, 에이전트별 파일

## 2단계: 작업 계획 접근방식
*이 섹션은 /tasks 명령어가 수행할 작업을 설명 - /plan 중에는 실행하지 않음*

**작업 생성 전략**:
- `.specify/templates/tasks-template.md`를 기본으로 로드
- 1단계 설계 문서(계약서, 데이터 모델, 빠른시작)에서 작업 생성
- 각 계약서 → 계약 테스트 작업 [P]
- 각 엔티티 → 모델 생성 작업 [P]
- 각 사용자 스토리 → 통합 테스트 작업
- 테스트를 통과시키는 구현 작업

**순서 전략**:
- TDD 순서: 구현 전에 테스트
- 의존성 순서: 모델 → 서비스 → UI
- 독립 파일에 대해 병렬 실행 [P] 표시

**예상 출력**: tasks.md에 25-30개의 번호가 매겨진 순서대로 정렬된 작업

**중요**: 이 단계는 /plan이 아닌 /tasks 명령어로 실행됩니다

## 3단계+: 향후 구현
*이러한 단계들은 /plan 명령어 범위를 벗어남*

**3단계**: 작업 실행 (/tasks 명령어가 tasks.md 생성)
**4단계**: 구현 (헌법 원칙에 따라 tasks.md 실행)
**5단계**: 검증 (테스트 실행, quickstart.md 실행, 성능 검증)

## 복잡도 추적

| 위반사항 | 필요한 이유 | 거부된 더 간단한 대안과 그 이유 |
|-----------|------------|-------------------------------------|
